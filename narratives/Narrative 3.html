Ricky Suarez CS 499 Milestone Four Enhancement Three Narrative: Databases Artifact Description The artifact I selected is the Grazioso Salvare Rescue Dog Dashboard, which I originally created in CS 340. The dashboard is a Python application that uses Dash, pandas, Plotly, Dash Leaflet, and MongoDB to help an animal rescue organization review shelter records. Users can view animal information in an interactive table, select different rescue categories, review ranked rescue candidates, display an animal’s location on a map, and examine animal outcome information through a bar chart. The application also uses a separate CRUD Python module to manage communication between the dashboard and the MongoDB database. I selected the same artifact for all three enhancement categories because it contains software design, algorithmic processing, and database functionality within one complete application. For Milestone Four, I focused specifically on strengthening how the application stores, retrieves, organizes, and protects its MongoDB data. Justification for Including the Artifact I included the Grazioso Salvare Dashboard in my ePortfolio because it demonstrates my ability to connect a user facing application to a nonrelational database and use stored information to support organizational decisions. The original application could retrieve animal records and perform basic create, read, update, and delete operations. However, the original database design did not include indexes for common searches, aggregation pipelines for reports, or audit records for administrative operations. These limitations meant the application worked, but it did not demonstrate the database controls and optimization techniques expected in a more professional system. For this enhancement, I added compound indexes that support the fields commonly used when evaluating rescue candidates. The main compound index includes animal_type, sex_upon_outcome, breed, and age_upon_outcome_in_weeks. These fields are frequently involved in the rescue selection process, so organizing them within an index can help MongoDB locate matching records without examining every document in the collection. I also added a separate index for animal_id, which supports direct animal lookups and the aggregation process used by the dashboard chart. I added MongoDB aggregation pipelines to move reporting work from pandas into the database. The outcome chart previously used pandas to count the values in the outcome_type column after the records had already been loaded into the notebook. The enhanced version gathers the animal IDs currently represented in the dashboard table and sends them to the CRUD module. MongoDB then uses a pipeline with the $match, $group, $sort, and $project stages to calculate the outcome totals. This demonstrates my ability to use database side processing rather than relying entirely on application side calculations. I also created a breed aggregation method that can identify the most common breeds matching a selected query. Although this method is not required for the visible dashboard layout, it demonstrates how the database module can be reused for future reports and administrative features. Another major improvement was the addition of an animal_audit_logs collection. The create, update, and delete methods now record information such as the operation type, timestamp, status, affected document count, and query used. Rejected operations are also logged, including attempts to perform an update or delete without a specific query. This provides a record of important database activity and can help an administrator investigate errors or unexpected changes. The audit records do not include usernames, passwords, or other connection credentials. The application continues to load its database username and password through environment variables. This supports authenticated database access without storing credentials directly in the notebook or CRUD module. A dedicated MongoDB user can also be assigned only the database permissions needed by the dashboard. The actual enforcement of those permissions depends on the MongoDB server configuration, but the application is structured to use an authenticated account rather than a hardcoded unrestricted connection. Reflection on the Enhancement Process The most important lesson I learned during this enhancement was that database design should be based on how an application actually uses its data. Adding indexes to every field would not automatically make the application better. Each index requires storage and can add work when documents are inserted or updated. I therefore focused on fields connected to the dashboard’s common rescue searches and reporting operations. This helped me understand the tradeoff between faster reads and the additional cost of maintaining indexes. I also learned the difference between performing data processing in the application and performing it inside the database. The original outcome chart produced correct results with pandas, but it required the notebook to receive the records and count them itself. The aggregation pipeline allows MongoDB to perform the grouping and sorting before returning the summarized result. This approach can reduce unnecessary data processing in the application, especially when working with a larger collection. One challenge was making sure the aggregation pipeline represented the records currently displayed in the dashboard. The table may show all animals or only the top ranked rescue candidates. To keep the chart synchronized with the table, I collected the visible animal_id values and used them in the pipeline’s $match stage. I also added checks to prevent an empty list of IDs from accidentally causing an aggregation across the entire collection. Another challenge was adding database features without changing the dashboard’s visible behavior. The radio options, ranked candidates, map, table, and chart placement were already working. The database enhancement was intended to improve the system behind the interface rather than redesign the interface. As a result, users may not see a major visual difference, but the chart now receives its counts from MongoDB instead of pandas, and the database now includes indexes and administrative records that improve the system’s structure. Audit logging also required careful consideration. An audit system should record enough information to explain what occurred without storing passwords or other sensitive information. I recorded the action, status, query, timestamp, affected count, and selected details while keeping authentication information out of the logs. I also learned that audit logging should not cause the main application to crash if the audit collection is temporarily unavailable, so audit failures are handled separately.
