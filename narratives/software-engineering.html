Ricky Suarez CS 499 Milestone Two Enhancement One Narrative: Software Design and Engineering Artifact Description The artifact I selected is the Grazioso Salvare Rescue Dog Dashboard that I originally created during CS 340. The application uses Python, Dash, pandas, Dash Leaflet, Plotly, and MongoDB to help Grazioso Salvare identify animals that may be suitable for different rescue roles. Users can filter the animal records by water rescue, wilderness rescue, or disaster and tracking categories. The dashboard then presents the matching records in an interactive table, displays the selected animal on a map, and creates a chart showing the frequency of animal outcome types. A separate Python module provides the create, read, update, and delete operations used to communicate with the MongoDB animal collection. Reason for Including the Artifact I selected this artifact for my ePortfolio because it demonstrates several areas of software development within one complete application. It includes a user interface, database communication, data filtering, interactive visualizations, and event driven callbacks. The original project successfully met the requirements of CS 340, but my code review identified several weaknesses that reduced its security, reliability, and maintainability. These included hardcoded credentials, a constructor that ignored the configuration values passed into it, broad exception handling, unsafe update and delete methods, and map code that accessed information through fixed numerical column positions. For this enhancement, I improved the CRUD Python module so the constructor now uses the username, password, host, port, database, and collection values supplied by the application. I added validation for the MongoDB connection settings and replaced general exception handling with MongoDB specific error handling. The create and read methods now validate their arguments before accessing the database. The update and delete methods reject empty queries so they cannot accidentally modify or remove every document in the collection. The update method also supports regular field dictionaries by placing them inside the MongoDB $set operator when necessary. I also improved the dashboard notebook without changing its main layout or intended behavior. The MongoDB username and password are now loaded through environment variables rather than being stored directly in the notebook. In the map callback, numerical column positions were replaced with descriptive column names such as location_lat, location_long, breed, and name. The callback now checks for empty data, missing columns, invalid coordinates, and outdated row selections before attempting to create the map. These changes make the program easier to understand and less likely to fail when the order of the DataFrame columns changes. Reflection on the Enhancement Process The most important lesson I learned during this enhancement was that improving software does not always require completely rewriting it. My first priority was to preserve the working dashboard while correcting the weaknesses identified during my code review. This required me to make targeted changes and test the application after updating both the CRUD module and notebook. I learned that even small design decisions, such as using a numerical column position instead of a field name, can create serious maintenance problems later. If the database or DataFrame column order changed, the original map could have displayed incorrect information or failed. One challenge was improving the CRUD functionality without breaking the existing MongoDB connection. The original constructor accepted several configuration values but ignored them in favor of hardcoded local settings. Updating it required me to ensure that the notebook and CRUD module continued to use the same constructor format. Moving the credentials into environment variables also required a different setup process before starting Jupyter, but this was a worthwhile tradeoff because the credentials no longer appear in the source code. Another challenge was protecting the update and delete operations. An empty MongoDB query can match every document, so the original methods could have modified or deleted the entire collection. Adding a requirement for a specific query made the methods safer, although it also means that any future administrative feature intended to update many records must provide an explicit condition.
